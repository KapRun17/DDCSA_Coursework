## 3.2 Реализация клиентской части

Клиентская часть веб-приложения реализована в репозитории проекта на GitHub [10]. Она отвечает за отображение интерфейса, навигацию между страницами, отправку запросов к серверному API и обработку пользовательских действий.

Для разработки клиентской части используется библиотека React и сборщик Vite. Приложение построено как SPA, поэтому переходы между основными разделами выполняются без полной перезагрузки страницы. Маршрутизация реализована с помощью React Router. В приложении выделены страницы главного каталога заявок, авторизации, регистрации, профиля, создания заявки, просмотра заявки, сообщений и административной панели.

Главная страница содержит каталог заявок. Пользователь может просматривать опубликованные заявки, фильтровать их по игре, типу шаблона и статусу, а затем переходить к подробной карточке заявки. Карточка заявки отображает игру, тип шаблона, роль, ранг, описание и автора. Если пользователь авторизован, он может отправить отклик на чужую заявку и добавить сообщение к отклику.

Страницы авторизации и регистрации работают с серверными маршрутами `/api/auth/login` и `/api/auth/register`. После успешного входа или регистрации клиентская часть сохраняет JWT-токен и данные пользователя в `localStorage`. Эти данные используются при последующих запросах к защищенным маршрутам. Также в интерфейс добавлена возможность выхода из аккаунта: при выходе локальная сессия очищается, а пользователь перенаправляется на страницу входа.

В профиле пользователя реализовано управление игровыми шаблонами и собственными заявками. При создании шаблона пользователь выбирает тип шаблона, игру, роль, ранг, расписание и описание. Для игры, роли и ранга используются выпадающие списки, что снижает количество ошибок при заполнении формы и делает дальнейшую фильтрацию заявок более предсказуемой. В профиле также отображаются собственные заявки пользователя, которые можно открыть, закрыть, открыть повторно или удалить.

Отдельная страница создания заявки позволяет сначала сохранить игровой шаблон, а затем опубликовать заявку на его основе. Такой сценарий соответствует выбранной модели данных: заявка не хранит игровые параметры напрямую, а связывается с заранее созданным шаблоном пользователя. Это позволяет повторно использовать один и тот же шаблон для разных заявок.

Для обмена сообщениями реализована страница диалогов. Пользователь видит список своих диалогов, может открыть выбранный диалог и отправить сообщение. Если отклик на заявку содержит текст, он также попадает в диалог между автором заявки и пользователем, отправившим отклик.

Административная панель доступна только пользователям с ролью `ADMIN`. В ней отображаются пользователи и заявки. Администратор может удалить профиль пользователя, изменить статус заявки, заблокировать заявку модератором или удалить ее. На клиентской стороне доступ к странице дополнительно ограничен проверкой роли, однако основная проверка прав выполняется на сервере.

Для взаимодействия с сервером в клиентской части выделены API-модули. Они инкапсулируют HTTP-запросы к серверу и используются страницами приложения. Общий HTTP-клиент добавляет JWT-токен в заголовок `Authorization`, если пользователь авторизован. Это позволяет не дублировать логику работы с токеном в каждой странице.

Клиентская часть также подготовлена к контейнеризации. Для нее создан `Dockerfile`, в котором приложение собирается через Vite, а готовые статические файлы размещаются в nginx. Конфигурация nginx настроена так, чтобы маршруты SPA корректно открывались при прямом переходе по адресу страницы.
