## 2.1 Выбор и обоснование клиент-серверной архитектуры

Для разрабатываемого веб-приложения выбрана клиент-серверная архитектура с разделением на клиентскую часть, серверное API и базу данных. Такой подход подходит для CRUD-приложения, в котором пользователь работает с интерфейсом в браузере, а основная обработка данных выполняется на сервере. В методических указаниях по разработке клиент-серверных приложений отдельно подчеркивается необходимость разделения пользовательского интерфейса, серверной логики и хранения данных, так как это упрощает сопровождение и дальнейшее развитие системы [1].

Клиентская часть представляет собой одностраничное веб-приложение. Пользователь открывает приложение в браузере и взаимодействует с каталогом заявок, профилем, шаблонами, откликами и сообщениями без постоянной перезагрузки страниц. При выполнении действий клиент отправляет HTTP-запросы к серверному API и получает ответы в формате JSON. Внутри клиентской части выделяются страницы и маршруты, API-клиент для обращения к серверу и локальное хранилище сессии.

Серверная часть отвечает за обработку запросов, проверку входных данных, аутентификацию пользователя, контроль ролей и выполнение операций с базой данных. В приложении выделяются обычный пользователь и администратор. Пользователь может создавать шаблоны, публиковать и удалять собственные заявки, отправлять отклики и обмениваться сообщениями. Администратор получает дополнительные права на модерацию заявок и удаление профилей. Логика проверки доступа размещается на сервере, поскольку клиентский интерфейс нельзя считать надежным источником ограничений безопасности.

Хранение данных выполняется в реляционной базе данных PostgreSQL. Сервер обращается к базе данных не напрямую из клиентской части, а через слой серверного приложения и ORM. Благодаря этому клиент не получает доступ к структуре базы данных и не может выполнять произвольные операции с сущностями. Конфигурационные параметры, такие как адрес API, строка подключения к базе данных и секрет JWT, должны передаваться через переменные окружения, что соответствует подходу Twelve-Factor App к хранению конфигурации приложения [4].

На диаграмме компонентов показано, что пользователь и администратор взаимодействуют с приложением через браузер. Клиентская часть включает страницы и маршруты React-приложения, API-клиент для отправки HTTP-запросов и локальное хранилище сессии, где сохраняются данные авторизованного пользователя. Серверная часть состоит из маршрутов API, middleware-слоя, контроллеров и Prisma Client. Middleware выполняет проверку JWT-токена, роли пользователя и входных данных, после чего запрос передается в соответствующий контроллер.

Слой Prisma Client связывает серверную логику с базой данных PostgreSQL. В базе данных хранятся пользователи, игровые шаблоны, заявки, отклики, диалоги и сообщения. Такое разделение компонентов позволяет изолировать пользовательский интерфейс от бизнес-логики и хранения данных, а также упрощает дальнейшую контейнеризацию и развертывание приложения.
