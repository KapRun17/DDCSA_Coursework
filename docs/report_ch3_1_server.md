## 3.1 Реализация серверной части

Серверная часть веб-приложения реализована в репозитории проекта, размещенном в системе контроля версий GitHub [10]. В данном подразделе рассматривается общая структура серверного приложения, основные маршруты API и принципы обработки запросов. Такой подход позволяет связать описание реализации с фактическим исходным кодом, не перегружая отчет дополнительными рисунками.

Серверное приложение разработано на платформе Node.js с использованием фреймворка Express. Точкой входа является файл `index.js`, в котором загружаются переменные окружения, проверяется подключение к базе данных PostgreSQL и запускается HTTP-сервер. Основная настройка приложения вынесена в файл `app.js`: в нем подключаются middleware, регистрируются маршруты API и задается единый обработчик ошибок.

В серверной части используется модульная структура. Маршруты расположены в каталоге `routes`, контроллеры — в каталоге `controllers`, middleware — в каталоге `middleware`, а подключение к Prisma Client вынесено в отдельный модуль. Такое разделение делает код более читаемым: маршруты отвечают за прием HTTP-запросов, middleware — за проверку токена, ролей и входных данных, а контроллеры — за выполнение основной бизнес-логики.

Для аутентификации используется JWT-токен. После регистрации или входа сервер формирует токен и передает его клиентской части. При обращении к защищенным маршрутам клиент отправляет токен в заголовке `Authorization`. Middleware аутентификации проверяет токен, извлекает данные пользователя и передает их дальше по цепочке обработки запроса. Для административных действий дополнительно используется middleware проверки роли.

Работа с базой данных выполняется через Prisma Client. В серверной части не формируются SQL-запросы вручную: контроллеры обращаются к Prisma-моделям, а ORM формирует запросы к PostgreSQL. Это уменьшает количество однотипного кода и позволяет связать программную реализацию с ER-моделью, описанной в предыдущей главе.

Основные маршруты серверного API представлены в таблице 3.1.

Таблица 3.1 — Основные маршруты серверного API

| Метод | Маршрут | Назначение | Доступ |
|---|---|---|---|
| GET | `/api/health` | Проверка работоспособности API | Открытый |
| POST | `/api/auth/register` | Регистрация пользователя | Открытый |
| POST | `/api/auth/login` | Авторизация пользователя | Открытый |
| GET | `/api/auth/me` | Получение данных текущего пользователя | Авторизованный пользователь |
| GET | `/api/users` | Получение списка пользователей | Администратор |
| GET | `/api/users/:id` | Получение данных пользователя | Авторизованный пользователь |
| PUT | `/api/users/:id` | Обновление данных профиля | Владелец профиля или администратор |
| DELETE | `/api/users/:id` | Удаление профиля | Администратор |
| GET | `/api/templates` | Получение шаблонов текущего пользователя | Авторизованный пользователь |
| POST | `/api/templates` | Создание игрового шаблона | Авторизованный пользователь |
| PUT | `/api/templates/:id` | Редактирование игрового шаблона | Владелец шаблона |
| DELETE | `/api/templates/:id` | Удаление игрового шаблона | Владелец шаблона |
| GET | `/api/requests` | Получение каталога заявок | Открытый |
| GET | `/api/requests/:id` | Получение детальной информации по заявке | Открытый |
| POST | `/api/requests` | Создание заявки | Авторизованный пользователь |
| PUT | `/api/requests/:id` | Обновление собственной заявки | Владелец заявки или администратор |
| PATCH | `/api/requests/:id/moderation` | Модерация статуса заявки | Администратор |
| DELETE | `/api/requests/:id` | Удаление заявки | Владелец заявки или администратор |
| POST | `/api/requests/:id/responses` | Отправка отклика на заявку | Авторизованный пользователь |
| GET | `/api/messages/conversations` | Получение списка диалогов | Авторизованный пользователь |
| GET | `/api/messages/conversations/:id` | Получение выбранного диалога | Участник диалога |
| POST | `/api/messages/conversations/:id/messages` | Отправка сообщения в диалог | Участник диалога |

Валидация входных данных выполняется на уровне маршрутов с помощью `express-validator`. Для регистрации проверяются имя пользователя, email и пароль, для шаблонов — тип шаблона, игра, название, роль, ранг и описание, для заявок — выбранный шаблон, заголовок, описание и статус. Если данные не соответствуют ограничениям, сервер возвращает ошибку до выполнения бизнес-логики контроллера.

Отдельное внимание уделено ролевой модели. Обычный пользователь может изменять только собственные шаблоны и заявки, а также отправлять отклики на чужие заявки. Администратор получает доступ к списку пользователей, удалению профилей и модерации заявок. Если заявка была заблокирована модератором, обычный пользователь не может самостоятельно вернуть ее в открытое состояние.

Для подготовки демонстрационных данных реализован seed-скрипт. Он создает тестового администратора, обычных пользователей, игровые шаблоны, заявки, отклик и диалог. Это позволяет быстро проверить основные сценарии приложения после настройки базы данных.

В рамках продолжения разработки была добавлена Docker-конфигурация. Для серверной части подготовлен `Dockerfile`, а в корне проекта создан `docker-compose.yml`, который объединяет PostgreSQL, серверное приложение и клиентскую часть. Это потребуется для последующего описания контейнеризации и развертывания приложения.
