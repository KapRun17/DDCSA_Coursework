## 3.3 Реализация аутентификации, авторизации и ролевой модели

Аутентификация и авторизация пользователей реализованы в серверной и клиентской частях проекта, размещенного в репозитории GitHub [10]. Данный функционал используется для входа в систему, защиты личного профиля, создания заявок, отправки откликов, обмена сообщениями и доступа к административной панели.

Регистрация пользователя выполняется через маршрут `/api/auth/register`. При создании учетной записи сервер проверяет имя пользователя, адрес электронной почты и пароль. Пароль не сохраняется в открытом виде: перед записью в базу данных он хешируется с помощью `bcryptjs`. При повторной регистрации с уже существующим email или именем пользователя сервер возвращает ошибку.

Авторизация выполняется через маршрут `/api/auth/login`. Сервер находит пользователя по email и сравнивает переданный пароль с сохраненным хешем. Если данные корректны, формируется JWT-токен. В полезную нагрузку токена помещаются идентификатор пользователя и его роль. Срок действия токена ограничен, что снижает риск длительного использования устаревшей сессии.

На клиентской стороне токен и данные пользователя сохраняются в `localStorage`. При последующих запросах общий HTTP-клиент добавляет токен в заголовок `Authorization` в формате `Bearer`. Если пользователь выходит из аккаунта, локальная сессия очищается, после чего интерфейс перенаправляет его на страницу входа.

Защита серверных маршрутов выполняется с помощью middleware аутентификации. Оно проверяет наличие заголовка `Authorization`, извлекает JWT-токен, проверяет его подпись и добавляет данные пользователя в объект запроса. Если токен отсутствует или недействителен, сервер возвращает ошибку `401`.

Ролевая модель включает две роли: `USER` и `ADMIN`. Обычный пользователь может управлять собственными шаблонами и заявками, отправлять отклики и участвовать в диалогах. Администратор имеет расширенные права: он может просматривать список пользователей, удалять профили, изменять статус заявок и блокировать некорректные заявки.

Для проверки административных действий используется отдельное middleware проверки роли. Оно сравнивает роль текущего пользователя со списком разрешенных ролей для маршрута. Если пользователь не обладает нужными правами, сервер возвращает ошибку `403`.

Дополнительные проверки выполняются внутри контроллеров. Например, пользователь не может создать заявку по чужому шаблону, изменить чужую заявку или откликнуться на собственную заявку. Если заявка была заблокирована администратором, обычный пользователь не может самостоятельно вернуть ее в открытое состояние. Это позволяет не ограничиваться только проверкой роли и учитывать владельца конкретной сущности.

На клиентской стороне роль пользователя используется для отображения элементов интерфейса. Например, ссылка на административную панель показывается только пользователю с ролью `ADMIN`. При этом основная проверка прав выполняется именно на сервере, так как клиентская проверка может быть обойдена.
